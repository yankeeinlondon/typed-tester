# Test Command Counting Improvement

**Date**: 2025-10-23
**Status**: Ready for Implementation
**Owner**: Claude Code

## Problem Statement

The `test` command currently reports test counts that differ significantly from Vitest's counts, creating confusion for users. For example:

**Current behavior:**

```txt
✓  tests/unit/utils/urlLink.test.ts (26 tests, 232ms, 789μs/line)
```

**Vitest behavior (same file):**

```txt
✓ tests/unit/utils/urlLink.test.ts (13 tests) 3ms
```

### Root Cause

The current implementation appears to be counting each `it` block twice - once for runtime tests and once for type tests, resulting in doubled counts. This creates several issues:

1. **Inconsistent terminology**: The word "tests" means different things in Vitest vs the `test` command
2. **Lack of granularity**: Users can't distinguish between `it` blocks and type assertions
3. **Missing information**: No indication of how many tests actually contain type tests
4. **Timing display issues**: Timing metrics are only shown when thresholds are exceeded, and formatting could be improved

## Proposed Solution

### New Counting System

Introduce three distinct metrics to provide better granularity:

1. **Tests**: Count of `it`/`test` blocks (matches Vitest nomenclature)
2. **Type Tests**: Count of `it` blocks that contain `type cases = [...]` declarations
3. **Assertions**: Count of individual type assertions within `type cases` arrays

### New Output Format

**File line format WITHOUT `--metrics` flag:**

```txt
✓  tests/unit/detection/preferred-language.test.ts (16 tests, 8 type tests, 38 assertions) 34ms
```

**File line format WITH `--metrics/-m` flag:**

```txt
✓  tests/unit/detection/preferred-language.test.ts (16 tests, 8 type tests, 38 assertions) 34ms | 968μs/line
```

### Timing Display Improvements

**Always show milliseconds:**

- Currently: Only shown when threshold exceeded
- New: Always shown for every file

**Color coding:**

- Fast tests (below threshold): Dimmed gray text with reduced font weight
- Slow tests (warning threshold): Orange/yellow text (existing)
- Very slow tests (critical threshold): Red text (existing)

**μs/line metric:**

- Currently: Shown inline with ms, comma-delimited
- New: Only shown with `--metrics/-m` flag
- Separator: ` | ` instead of comma

## Implementation Plan

This plan is broken into 4 phases following TDD principles.

---

## Phase 1: AST Analysis Enhancement

**Goal**: Enhance the AST parsing to distinguish between runtime tests and type tests, and count type assertions.

### Tasks

1. **Update TypeTest interface** to include:
   - `hasTypeCases: boolean` - whether this test contains type assertions
   - `typeAssertionCount: number` - count of assertions in the `type cases` array

2. **Enhance `asTestFile()` in `src/ast/testing.ts`**:
   - Detect presence of `type cases = [...]` declarations within each `it` block
   - Count elements in the `type cases` tuple type array
   - Extract this information during AST traversal

3. **Update `TestFile` interface** to aggregate:
   - Total type test count (tests with `hasTypeCases = true`)
   - Total assertion count (sum of all `typeAssertionCount`)

### Success Criteria

- [ ] TypeTest interface updated with new fields
- [ ] AST parser correctly identifies type cases declarations
- [ ] AST parser correctly counts tuple elements in type cases arrays
- [ ] TestFile interface has aggregated counts
- [ ] All existing tests pass (no regressions)
- [ ] New tests verify type case detection and counting

---

## Phase 2: Test Command Counting Logic

**Goal**: Update the test counting logic throughout the codebase to use the new three-metric system.

### Tasks

1. **Update `calculateTestSummary()` in `src/commands/test.ts`**:
   - Change `tests` count to count `it` blocks (not doubled)
   - Add `typeTests` count (tests with type assertions)
   - Add `assertions` count (total type assertions)

2. **Update `TestSummary` interface** in `src/types/testing-types.ts`:
   - Add `typeTests: number` field
   - Add `assertions: number` field

3. **Update all code that references test counts**:
   - `showTestFile()` in `src/report/showTestFile.ts`
   - `showTestSummary()` in `src/report/showTestSummary.ts`
   - Any other files that reference test counts

### Success Criteria

- [ ] TestSummary interface has new fields
- [ ] calculateTestSummary correctly computes all three metrics
- [ ] Test count matches Vitest's count (no more doubling)
- [ ] All existing tests pass
- [ ] New tests verify the counting logic

---

## Phase 3: Display Format Updates

**Goal**: Update the output formatting to show the new metrics and timing information.

### Tasks

1. **Update `showTestFile()` in `src/report/showTestFile.ts`**:
   - Display format: `(X tests, Y type tests, Z assertions)`
   - Always show milliseconds timing
   - Only show `μs/line` when `--metrics` flag is used
   - Use ` | ` separator between count metrics and timing metrics
   - Apply new color coding for timing:
     - Fast: dimmed gray
     - Slow: orange/yellow (existing)
     - Very slow: red (existing)

2. **Add `--metrics/-m` CLI flag** in `src/cli/create_cli.ts`:
   - Short form: `-m`
   - Long form: `--metrics`
   - Description: "Show additional performance metrics (μs/line)"

3. **Update timing display logic**:
   - Refactor timing color logic into helper function
   - Apply dimming for fast tests
   - Maintain existing warning colors

### Success Criteria

- [ ] File output shows new format with all three metrics
- [ ] Milliseconds always displayed
- [ ] μs/line only shown with --metrics flag
- [ ] Color coding works correctly for all speed categories
- [ ] --metrics flag properly toggles μs/line display
- [ ] All existing tests pass

## Notes

- This is a breaking change in how metrics are reported, but it's a positive change that improves clarity
- The change makes the tool more consistent with industry standard tools (Vitest)
- Users may need to update any scripts that parse the test command output
- Consider adding a release note explaining the change

## Open Questions

1. Should we show type test count even when it's 0?
   - **Proposal**: Yes, for consistency: `(13 tests, 0 type tests, 0 assertions)`
   - **Alternative**: Hide when zero: `(13 tests)`

2. Should slow file detection consider type assertion count?
   - **Current**: Based on duration and duration/lines ratio
   - **Proposal**: Keep current behavior, may revisit later

3. Should JSON output include the new fields?
   - **Proposal**: Yes, add to TestFile and TestBlock interfaces
