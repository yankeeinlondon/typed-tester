# `test` Reporting

In this plan we will be improving the `test` command.

## Expected Test Reporting Structure

```txt
file
 | 
 |- (optional: Areas OUTSIDE of tests blocks)
 |
 |─ `describe` block
        |
        |- (optional: Areas OUTSIDE of tests blocks)
        |
        |- `it` block
               |
               |- assertions
```

- the top level `describe` block is ok to skip if there is only ONE top level `describe` block otherwise it should always be shown
- `describe` blocks below the top level should ALWAYS be shown

I think i'm seeing other examples where the reporting structure illustrated above is not being handled well. 

## Tests with no Type Tests

I think we should change our policy of when we show test files that have no/zero type tests:

- by default we should NOT show test files that have no type tests
  - this also means that we may need to adjust how we express the test summary at the end because currently we're providing both TOTAL tests and TESTS WITH TYPE TESTS. 
  - because the concept of TOTAL TESTS (aka non type tests + type tests) doesn't exist in this non-verbose report we should simplify the language
- if `--verbose` flag is turned on then:
  - for tests with ZERO type tests:
    - we will add in a "de-emphasized" text line for the file but there is no need to go into the details beyond the top line.
  - for tests with SOME type tests:
    - we will continue reporting largely as we have been: all `describe` and `it` blocks under the test are shown.

## One more bug

Also I noticed this when I ran our own tests:

```txt
⤬  tests/unit/test-command/counting-logic.test.ts (9 tests, 0 type tests, 0 assertions) 14ms
    [ ✓ ] TestSummary interface [3 tests, no errors]
    [ ⤬ ] calculateTestSummary() counting logic [6 tests, 1 type error]
          [ ✔ ] should count total tests across all files
          [ ✔ ] should aggregate typeTests from all TestFile objects
          [ ✔ ] should aggregate assertions from all TestFile objects
          [ ✔ ] should handle files with no type tests
          [ ✔ ] should handle mixed files (some with type tests, some without)
          [ ✔ ] should not double-count tests
```

- i'm unclear why at the file level we report with this format `9 tests, 0 type tests, 0 assertions` but then at the describe block level we report `6 tests, 1 type error`.
- I'm ok with one being enclosed in parenthesis and the other square brackets but not that we're reporting on different things.
- A user should reasonably be able to see more detailed levels of the heirarchy
