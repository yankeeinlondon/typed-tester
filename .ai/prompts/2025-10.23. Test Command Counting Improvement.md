# Test Command Counting Improvement

When we have a completely successful type test run with the `test` command we might see something like:

```txt
 ✓  tests/unit/detection/preferred-language.test.ts (32 tests)
 ✓  tests/unit/utils/ssmlParser.test.ts (114 tests) 
 ✓  tests/unit/utils/voiceFallback.test.ts (63 tests) 
```

However, when I use Vitest to run runtime tests on the same exact files I get output like:

```txt
 ✓ tests/unit/detection/preferred-language.test.ts (16 tests) 3ms
 ✓ tests/unit/utils/ssmlParser.test.ts (38 tests) 4ms
 ✓ tests/unit/utils/voiceFallback.test.ts (21 tests) 4ms
```

What's important to understand is that both _runners_ (e.g., Vitest and the `test` command here) use the same `describe` and `it` blocks to structure testing. In general that's a good thing. However, it is concerning the the test counts _per file_ are so different. I suspect, but don't know, that the variance is due to the `test` command not counting the number of `it` blocks as tests but rather every test which is executed inside the `cases` test blocks which are an array of binary assertions.

I think for type testing we need to be consistent in how we report but I think it's also useful to be _additive_ in what we present. The main thing we need to avoid is unexplained conflicts in naming.

## Proposed Solution

- the `it` blocks should be called "tests" in both Vitest and the `test` command
    - that IS the nomenclature that Vitest already uses
    - it appears NOT to be the nomenclature the `test` command uses
- in type testing the individual test assertions inside the `cases` type should be called "assertions"
    - it's true that often an _assertion_ and a _test_ are seen to be the same thing
    - but in a way these terms would both be a test but they would vary in _granularity_
- the reporting structure would benefit from also having a count of how many "tests" actually have any type-tests in them (it's not uncommon to have a purely runtime based test inside a `it` block)

With the above considerations, let's take a single file's successful output in the "new" format:

```txt
✓  tests/unit/detection/preferred-language.test.ts (16 tests, 8 type tests, 38 assertions)
```

When a test takes longer than a certain threshold we report on timing in both `ms` and `μs/line` and use a color coding scheme which goes from orange to red. In the "new" layout we will:

- report `ms` regardless of whether we're below any threshold but we will continue to use color information:
    - any file which is below the current threshold will be displayed "dimmed" (font weight) and a grayish color (which has enough contrast for both light and dark consoles)
    - the color of the timing will be still be made orange and then red when the timing thresholds are hit
- the metric `μs/line` will not be displayed by default but will be brought in when using a new CLI flag `--metrics`/ `-m` flag is used
    - currently the two metrics -- when presented together -- are comma delimited and inside the same parenthesis which show the count metrics.
    - in the new design both metrics will be after the parenthesis (just like Vitest does) and instead of being comma delimited they will be ` | ` delimited.

Here's the line structure you'd see WITHOUT the `-m` flag for a successful file:

```txt
✓  tests/unit/detection/preferred-language.test.ts (16 tests, 8 type tests, 38 assertions) 34ms
```

and WITH the `-m` flag:

```txt
✓  tests/unit/detection/preferred-language.test.ts (16 tests, 8 type tests, 38 assertions) 34ms | 968μs/line
```
